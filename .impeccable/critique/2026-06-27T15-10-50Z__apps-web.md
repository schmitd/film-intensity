# Anti-Patterns Verdict

**LLM assessment**: This does not immediately read as generic AI output. The dark committed palette, OKLCH tokens, serif display voice, and Garmin/movie specificity give it a real point of view. The main AI tells are structural: every major section uses the same small dot label rhythm, the homepage hero leans on metric-card framing, and the operational flow is presented as an editorial sequence rather than a task surface.

# Overall Impression

The web app has a strong cinematic-console foundation and better-than-average product taste. The biggest opportunity is to stop treating the homepage like a persuasive landing page and make it a reliable live operating console: clear current state, obvious next action, pair-code recovery, and better semantics around "recording", "paired", "complete", and "unsupported".

# What's Working

- The visual direction is distinctive and appropriate. The dark ink/ember/cyan/gold system in `globals.css` supports dim-room use and avoids generic SaaS light mode.
- The film rows are more interesting than a card grid. Ranking, logline, metadata, band, and score are scannable in one row without falling into identical card repetition.
- Empty states in the timeline and moment list teach the system instead of saying "nothing here"; they explain that completed Garmin sessions generate the missing data.

# Priority Issues

**[P1] The primary task flow loses operational clarity after session creation**

**Why it matters**: The core user outcome is create session, pair watch, record movie, then see intensity. The UI gets the user to a pair code, but it does not give them a durable control surface for copying the code, starting another run, canceling/resetting, seeing expiration, or confirming watch connection.

**Fix**: Promote created-session output into a task module with copy code, expires/created time, selected film, next watch step, pairing status placeholder, and "create another session" or "discard" action. Treat it as a state machine, not a success card.

**Suggested command**: `$impeccable harden apps/web/components/create-session-form.tsx`

**[P1] Product IA is still homepage/editorial, not command-console**

**Why it matters**: The product is a tool. The current page begins with a brand-style hero, then featured films, then setup, then operations. For a pilot operator, the most important question is "what is live, what needs action, and how do I start/continue a run?"

**Fix**: Reorder the dashboard around operational priority: active capture and session setup first, then film leaderboard, then recent history. Use a compact status rail or top bar for films/completed/live/average instead of hero metric cards. Keep the cinematic voice, but let task priority drive layout.

**Suggested command**: `$impeccable layout apps/web/app/page.tsx`

**[P1] Error prevention is weak around consent, disabled fields, and device capabilities**

**Why it matters**: Biometrics are sensitive even when framed as entertainment analytics. Pre-checking consent, showing disabled metadata as form fields, and hiding device capability consequences makes the flow feel less trustworthy than the visual design suggests.

**Fix**: Require explicit consent each new session, render runtime/director as read-only metadata rather than disabled inputs, and add short capability notes for HRV/stress availability before session creation.

**Suggested command**: `$impeccable harden apps/web/components/create-session-form.tsx`

**[P2] The timeline is visually present but analytically under-explained**

**Why it matters**: The design principles say the timeline is the hero, but the film detail page renders a list of bars without axis context, segment landmarks, sample confidence, or explanation of what `100` means. Users can see spikes but not trust or interpret them.

**Fix**: Add a timeline legend, runtime markers, peak annotations, viewer/sample count context, and plain-language scoring definition. Consider compressing dense five-second buckets into a primary curve plus inspectable rows.

**Suggested command**: `$impeccable clarify apps/web/components/timeline.tsx`

**[P2] Repeated section labels and numbered scaffolding weaken the otherwise distinctive voice**

**Why it matters**: The dot-prefixed label appears on nearly every section, and the 01/02/03 setup sequence adds a common generated-page cadence. The content is specific, but the framing pattern is familiar enough to flatten the brand.

**Fix**: Keep one named product label style, then vary the rest: dashboard headers, inline status groups, command panels, and real stepper treatment only where the sequence is interactive or stateful.

**Suggested command**: `$impeccable quieter apps/web`

# Persona Red Flags

**Pilot Screening Host**: They want to start a movie with friends in the room. The pair code appears only after form submission, but there is no copy action, no expiration, no "watch connected" confirmation, and no recovery path if the watch app is opened late. The host is likely to leave the laptop open and hope the state is still valid.

**First-Time Garmin User**: The setup copy says Venu-first and HRV/stress, but it does not tell them what they will see on the watch after entering the pair code. "Keep the app foregrounded" is useful, but it appears before the user has actually paired, so it is easy to skim past.

**Data-Skeptical Film Fan**: They can see "overdrive", "100", and "five-second buckets", but not what the score is normalized against or how many viewers generated a spike. They will question whether the visualization is meaningful or just decorative telemetry.

# Minor Observations

- The `Runtime` and `Director` fields are disabled inputs, which implies form controls instead of stable metadata.
- `button` and `.button` share styling, but anchor buttons need consistent disabled/unavailable patterns if future flows require blocked navigation.
- Motion is modest and has reduced-motion handling, but the same `settle-in` animation is applied to multiple unrelated component types; product UI should reserve motion for state changes.
- The sign-in page is visibly a scaffold. That is acceptable for v1, but it should not be part of a polished pilot demo unless its language is reframed as intentional access gating.
- The film detail back link says "Back to command surface"; "dashboard" or "session dashboard" would be clearer.

# Questions to Consider

- What if the default dashboard opened on "Active capture + Start session" instead of a hero?
- What has to be true on screen for a host to confidently press play on the movie?
- Should "intensity" be a spectacle score, an analytic signal, or both? The current UI tries to be both without explaining the boundary.
- What would make the watch-pairing moment feel as trustworthy as a two-factor authentication flow?
